## Architecture notes carried forward to Phase 5

**Same-key severity escalation is architecturally deterministic under daily-close replay — a real finding from building Phase 4's live demo, not a bug.** Each `(ticker, trading_day, signal_type)` is scored from a fixed close price and a fixed (static, Phase 2) baseline — re-scoring the same trading day at a later wall-clock time always reproduces the identical z_score and severity, because neither input has changed. This means genuine escalation for a fixed key **cannot** occur just by letting replay resume after a `stale`/`outage` fault and waiting — verified directly: recovering from a freeze and letting the scheduler naturally advance past the frozen tick reproduced the same severity every time. A real intraday feed (multiple ticks arriving through a single trading session, each with a different return-so-far) would exhibit genuine escalation organically; this project's one-close-per-day replay granularity does not have that texture. Documented here and in RELIABILITY.md rather than silently worked around. `backend/scripts/seed_demo_escalation_precondition.py` exists specifically to make the ack-bust mechanism observable live within a 5-minute demo window despite this: it seeds a single flag at an artificially low severity for a real, not-yet-reached (ticker, trading_day) and acks it — verifying beforehand, using the real unmodified scoring functions, what the true severity will be, and refusing to seed if the placeholder wouldn't actually be superseded. Everything downstream of that one constructed starting row (the correction, the ack-bust, the new severity) is 100% genuine, computed by the unmodified `run_scoring_cycle`/`upsert_flag_with_ack_bust` from real historical data, fired by the live scheduler — not a manual script call. Verified live on 2026-09-04 (see below).

**Demo-user identity is a single seam (`app/auth.py`), not real auth.** `get_current_user()` always returns one hardcoded UUID constant (`DEMO_USER_ID`). Every watchlist endpoint obtains the current user only through this dependency (never off a request field or invented inline), and checks `watchlist.user_id == current_user` via `app/services/watchlist_access.py::get_owned_watchlist()` — a non-existent and a non-owned watchlist both 404 identically, no resource-existence leak. When real JWT verification is built, only `get_current_user()`'s body changes (decode the token, look up the user) — no endpoint logic or data model change required, because every call site already goes through this one function.

**Aggregate ETag hash — canonical scheme, locked.** `app/services/digest.py::compute_aggregate_hash()`: for every currently unacknowledged flag belonging to the watchlist's tickers, take `(flag_id, severity_rank)`, sort by `flag_id` ascending, serialize as `json.dumps([[flag_id, severity_rank], ...], separators=(',', ':'))`, SHA-256 hex digest of the UTF-8 bytes. Always recomputed fresh from committed DB state (the same join shape as DATA_MODEL.md's "what's changed since last check" query) — never cached, never trusts a client-supplied hash. Empty set hashes to a stable, defined value (`EMPTY_DIGEST_HASH`), not an error.

**`GET /digest` 304 semantics implemented via FastAPI's `Request`/`Response` directly**, not a framework-level ETag middleware — `If-None-Match` is compared against the freshly-computed hash per request; both the 200 and 304 paths set the `ETag` header explicitly.

**Evidence's mean_return/stdev_return/points now come from the exact same baseline row that produced the flag's stored z_score — corrected same-day, before commit.** The original Phase 3 implementation recomputed a 30-return window ending at the flag's own `trading_day` independently of the baseline used at scoring time; because Phase 2's baseline is static, that window usually didn't match the one the stored z_score actually came from, so the displayed band and the displayed z_score could be mutually inconsistent — on the one screen whose entire purpose is proving the system isn't a black box. Fixed in `app/services/evidence.py`: `mean_return`/`stdev_return` are read directly from `load_latest_baseline()` (the same call the scoring engine used), and `points` is the exact window that baseline's own stats were computed from. The flagged day's own return is fetched separately (it may fall outside that plotted window, since the baseline is static) — `flagged_point.z_score` is the flag's stored value, and it is now algebraically reproducible as `(flagged_point.return - mean_return) / stdev_return` within floating-point/NUMERIC(6,3)-rounding tolerance. Verified both in a dedicated test (`test_flagged_point_zscore_is_reproducible_from_response`) and manually against a real Phase 2 flag (EICHERMOT.NS, 2025-09-05): recomputed z = 2.178039 vs. stored 2.178, diff ~4e-5.

**Live APScheduler background job, replacing the "manual trigger only" state from Phase 2/3.** `backend/app/main.py`'s lifespan constructs the provider once, starts an `AsyncIOScheduler` job (`SCHEDULER_INTERVAL_SECONDS`, default 5s) that calls `run_scoring_cycle` then `provider.advance()`, and shuts it down cleanly on app shutdown. `run_scoring_cycle` (`app/services/scoring_pipeline.py`) is the exact per-tick logic extracted from Phase 2's `run_scoring_once.py` — both the manual script and the live scheduler call this one function, never duplicated. Test suite disables the scheduler job (`settings.scheduler_enabled = False`, still constructs the provider) so tests aren't racing a real 5s-interval background job; they exercise `run_scoring_cycle` directly instead, which the scheduler itself just calls on a timer.

**Freeze semantics — precise, per Phase 4's locked decisions.** `FaultInjectingProvider` (`app/providers/fault_injecting.py`) wraps `HistoricalReplayProvider`: `'stale'` freezes the replay position (`advance()` no-ops) but does NOT touch `age_seconds`, which is always real wall-clock time since `last_successful_fetch` — `age_seconds` grows naturally and crosses the configured thresholds purely because real time passes while the replay position doesn't move (verified live: age reached 48.7s real elapsed time while frozen). `'outage'` is a harder failure — `get_ticks()` raises, `get_status()` reports `UNAVAILABLE` immediately regardless of age. `'recover'` transitions back to `'normal'` but does NOT snap freshness back to LIVE — it stays whatever real elapsed time dictates until the next successful `get_ticks()` call refreshes `last_successful_fetch` (confirmed live: status stayed briefly non-LIVE immediately after recovery, then flipped to LIVE once the next natural scheduler tick fired). The scheduler's own interval is never altered by fault injection — `advance()` is simply a no-op internally while frozen, so the scheduler doesn't need to branch on fault mode at all.

**Freshness thresholds are demo-compressed, one configurable mechanism (`FRESHNESS_LIVE_SECONDS`/`_RECENT_SECONDS`/`_DELAYED_SECONDS`/`_STALE_SECONDS`, `app/config.py`).** Defaults: 5s/15s/30s/30s. A production deployment against real intraday/EOD equity data would reasonably use the original minutes-scale figures (15s/2min/10min); these are shortened specifically so live fault-injection is demonstrable within a 5-minute presentation instead of a 10+ minute real wait. No hardcoded threshold values anywhere in the freshness-state code (`app/services/freshness.py`) — see ARCHITECTURE.md.

**`provider_state` persists `mode`, `frozen_at`, AND `last_successful_fetch` across a process restart — corrected same-day, before commit.** The original Phase 4 implementation persisted only `mode`/`frozen_at` and documented the `last_successful_fetch` gap as a narrow, low-risk limitation. That claim was checked empirically with a simulated restart (see below) rather than taken on faith, and it was WRONG: freshness classification depends entirely on `age = now - last_successful_fetch` — `frozen_at` is cosmetic, only used in `detail`, and never enters the state computation. So a restart during a genuine `'stale'` fault reset the age clock to the restart moment and `get_status()` immediately reported **LIVE** despite the feed having been stale for real minutes beforehand — a correctness bug, not a narrow limitation. `'outage'` was independently confirmed safe across restart (its `UNAVAILABLE` branch never consults `age_seconds`). Fixed by adding a `last_successful_fetch` column (`migrations/002_add_last_successful_fetch.sql`) and persisting all three fields together via `FaultInjectingProvider.persist()` — called on every `/admin/fault` change and on every scheduler tick (bounding an unclean crash's freshness-precision loss to one scheduler interval, not the whole restart). Re-verified after the fix with the same simulated-restart method: `STALE` with `age_seconds > 290` correctly survived the simulated restart; two dedicated regression tests added (`test_restart_during_stale_correctly_preserves_staleness_not_reset_to_live`, `test_restart_during_outage_remains_unavailable`). Concurrent `/admin/fault` calls remain last-write-wins (a single UPSERT on the fixed `id=1` row) — no locking, unchanged.

**Manual trigger script, still available, now calls the shared pipeline.** `backend/scripts/run_scoring_once.py` still works standalone (its own plain, unwrapped `HistoricalReplayProvider`) but now calls `run_scoring_cycle` instead of duplicating the scoring loop.

**Baselines are static across replay days (Phase 2 simplification, not a bug) — unchanged in Phase 4.** Phase 1's backfill computes exactly one baseline row per ticker; nothing since has recomputed per replay day. See `load_latest_baseline()`'s docstring. Consequence for Phase 4 specifically: same-key severity escalation cannot occur from natural replay resumption alone — see the escalation-precondition note above.

**`trading_day` derives from the replay tick's own timestamp, never wall-clock time (Phase 2 decision, still load-bearing).** `scoring.trading_day_from_tick()` returns `tick.timestamp.date()`. Confirmed again in the Phase 4 live run: flags carried dates like `2026-02-16`, not `2026-09-04`.
